## 候補更新と環境上の注意

Android候補を1.0.18(19)、source `7e3fb4cd1853b113f8e37ee0f6beeb301838a514`として作成。正式鍵・非debuggable・版番号・runtime設定・compiled iconのcandidateゲートを通過し、4 AVDへinstall -r成功。公開releaseではない。

iOS Simulator候補は1.0(2026110907)。unsigned buildの後付けad-hoc署名ではリンク時`__entitlements`がなく、既存Keychainが読めず登録画面となった。過去の環境障害と同じ条件で、CODE_SIGNING_ALLOWED=YES、CODE_SIGN_IDENTITY=-、既存team/endpointのビルドへ置換すると**招待コード再入力なしで既存登録が戻った**。登録/Keychain消去は行っていない。標準手順へ「単にcodesign表示がadhocかだけで判定せず、署名有効でリンクした候補を使う」を追加する。

## 反復受信で見つかった問題（#65）

source 7e3fb4c / iOS0907・Android19、5送信者×3巡の予定で実行。1巡目の5送信/20受信UI観測は成功。2巡目のAndroid14送信中、iOSはRX_WAITING_FIRST_AUDIO→再接続となった。初期runnerはPTT消失をBLOCKEDと記録したが、保存XMLとjournalにより送信中のPRODUCT_FAILと別のレビュー記録で分類し直した。正常4回の最初のPCMは約0.8秒後、失敗回は約2.58秒のwatchdogで再接続し、その後同じ発話のPCMを観測した。音声聴取の証明ではない。

iOS→Android14だけの3巡（6送信/24受信UI）は旧候補でも成功し、「自送信の直後は必ず失敗」の仮説は否定された。Issue #65を作成、部分成功で閉じない。

630512fで正常END時のSDK unsubscribe→subscribeを除去し、世代フェンス完了だけに変更。SDKのunsubscribeは即座にtrackをnilにし、subscribeは非同期要求だけだった。異常復旧の強制購読更新は保持。古いruntimeのclear完了も無視する。RESTOREの理由/購読/PCM有無をjournalへ記録する。iOS332件（2skip/失敗0）、Android unit task、Python4件成功。間欠失敗の原因確定・実機解消は未証明。Simulator候補1.0(2026110908)を作成し、同じ5送信者行列で確認する。

候補0908の最初のREADY準備でAndroid14の登録照会が一時失敗し、手動の1回再試行後に登録消去なしでREADYへ復帰した。次の準備ではAPI36のUIAutomator dump自体が失敗した。これらを修正の合否に含めない。ネット断試験はAndroid14で12秒切断→復元12秒後にCONNECTED/READYを確認（後続PTTは別判定）。Android15では有限AudioFocus helperがGAIN_TRANSIENTを取得(result=1)、約10秒後にabandon、アプリ前面復帰後READYを確認した。実Auto投影/車載音響の代替ではない。

続く基盤調査でAPI36のQEMU main loop/CPU threadの15秒応答停止とADBからの消失を確認。UI失敗だけをアプリ不具合へ誤分類しない。データを保持して当該AVDを再起動し、5台のOS/build inventoryを再取得した。iOS0908の署名entitlementsを確認済み。

Android15のGAIN（恒久割込み）もhelper取得result=1、約10秒で解放。KOEONはINTERRUPTED＋「音声を再接続」を表示した。これは恒久LOSSの安全な明示復旧経路として扱う。再接続ボタン押下直後のUI取得はexit137となり、その瞬間の復帰判定は保留し、後続5台PTTゲートで別確認する。
