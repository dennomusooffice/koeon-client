## RXレベル追加要求（実装前）

所有者が音量レベル表示の実装を追加承認。SDKの既存受信PCM観測箇所からRMS dBFSを計算し、RAM内の数値だけを最大10HzでUIへ渡す。PCMを複製/キュー/保存/送信せず、再生や音量制御を変更しない。TX INは既存の入力RMS、RXはデコード後/端末出力音量前のRMSとして区別する。無音は-96dBFS、未取得/未対応形式/300ms以上古い値/切断は「—」。Androidの複数トラックは最新値の最大（混合音圧とは異なる）、iOSはSDK混合受信PCM。安全なバッファ境界、非有限値拒否、サンプル数上限、退出/旧トラックの無効化を検証。合成PCMで数値/無音/形式/失効回帰を追加し、指定実機で有限PTT送受信時のメーター更新と停止を確認する。聴取品質の証明とはしない。サーバー変更は不要で#43に計測契約を追記する。

所有者の外出中2時間の自律開発・試験指示により、指定2台の新しい許可枠を2026-11-11 18:02:20〜20:02:20 JSTとする。実機操作ガードもこの期限に更新。

TX表示は既存の発話全体平均（ゲイン学習用）とは別に、既存処理で算出済みのフレームRMSを一つだけRAM保持して使用する。学習/ゲイン/音声サンプル処理を変えず、UI読み取り10Hz・300ms失効と送信状態ゲートを適用。当初はRXもactive/draining期間だけ表示する案としたが、最終契約で以下の通り撤回。

実機ui04でTX中のレベルが未取得のままになる表示不具合を検出。RXの変化がないとStateFlowが同値snapshotを抑制し、TX読取りが起動しないことが原因。Roomの100ms更新snapshot自体にTXレベルを含め、RXなしでも変化を通知する。音声送信契約は変更なし。ui05で再検証。

iOSの名前一覧/前後選択はAndroidと同じ一覧オーバーレイへ統一。高頻度メーター更新中のネイティブポップアップMenuで実機自動操作の可視性判定が不安定だったため、固定した一覧から候補選択→LCD確定待ちへ戻す構成で再検証する。

中間候補ではRX表示を受信開始中も、実際に新鮮なPCM計測がある場合に限って許可する。発話検出/VADが無音でactiveにならなくても受信フレームは存在し得るため。Floor通知だけでメーターやLEDを点けず、待受idleでは消す案とした。最終メーター契約は下記の通り変更し、LEDだけ待受消灯を維持。

Android RXの未取得条件を調査。診断では受信PCM件数が増えており、無音/発話検出だけでは説明できない。SDKが再利用するByteBufferのpositionが末尾の場合、既存のremainingチェックが完全なフレームも拒否することを合成PCMで再現（218件中追加1件が修正前失敗）。duplicateをrewindし元bufferを変更せず先頭から指定フレームを読む。フレーム長/limit/形式の境界チェックは維持する。実機原因との一致は再導入後に検証し、Diagnosticsへビット深度/チャネル数/フレーム数/バッファ位置だけをRAMで表示して切り分ける（音声内容なし）。

Android実機ではSDK入力形式が16bit/mono/480frames/pos0/limit960と確認でき、バッファcursor不具合が今回の唯一の原因とは確定しなかった。RTC統計のエネルギー差分を補完経路にする試作も行ったが、実機で表示改善を確認できず不採用とした。最終候補に統計ポーリングは含めない。

最終メーター契約: RX制御状態による表示ゲートは撤回。接続中に新鮮なSDK PCM計測があればその実測値を表示し、無音は-96dBFS、未取得/形式不適合/300ms失効/切断は「—」とする。受信LEDは受信制御状態を示すため、待受では消灯を維持する。待受中のSDK無音コールバックが数値として表示されることは異常や受信中を意味しない。TXは送信中のゲイン前フレームRMSを表示する。
